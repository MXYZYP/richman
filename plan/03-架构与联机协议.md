## 1. 技术选型（已定，执行 agent 不再另选）

| 部分 | 选型 | 选择理由 |
|---|---|---|
| 包管理 | pnpm workspaces（monorepo） | 客户端/服务器/引擎共享代码与类型 |
| 语言 | TypeScript（全栈） | 类型即文档，跨包接口不易错 |
| 客户端 | Vue 3 + Vite + Pinia | 成熟、中文资料多、够用 |
| 棋盘渲染 | **DOM + CSS + 内联 SVG**（不用 canvas/游戏引擎） | 约 50 格 + 4 棋子的量级，DOM 完全流畅；调试、响应式、无障碍都更简单 |
| 服务器 | Node.js 20 + Socket.IO | WebSocket 实时双向通信的成熟方案，自带断线检测/自动重连/房间概念 |
| 规则引擎 | 独立纯函数包（无 UI、无网络、无 IO） | 同一份代码：阶段 1 在浏览器本地跑，阶段 2 原样搬进服务器；可被测试穷举 |
| 测试 | Vitest（引擎单测）+ Playwright（多浏览器联机 e2e） | 见各阶段文档验证要求 |
| 数据库 | **无**。内存 + JSON 文件存档 | 内部小规模房间（最多 6 参赛 + 3 观战），不引入数据库 |
| 账号 | **无**。房间码 + 昵称 + 本地令牌 | 见 §6 |

## 3. 服务器权威模型

- **唯一真相在服务器**（阶段 1 暂在浏览器本地，同一套引擎）。客户端只做两件事：把玩家操作变成 intent 发出去；把服务器回的状态和事件渲染出来。
- 客户端**不执行任何规则判定**（展示性计算除外，如"这块地当前租金多少"，通过复用 `@richman/engine` 的 selectors 得到，保证口径一致）。
- 服务器对每个 intent 做全量校验：是不是轮到你、当前阶段是否允许该操作、钱够不够、参数是否合法。非法即拒绝并返回错误码，状态不变。
- 这带来的直接好处：防作弊防不同步；断线重连只需重发一份快照。

## 4. 规则引擎接口（`@richman/engine`）

**纯函数、确定性、无副作用**——这是引擎可以被穷举测试、可以在浏览器和服务器两边跑的根基。

**模块化扩展点**（owner 需求，00 §4 决策 5）：① 游戏内容全部来自 `@richman/board-data` 的数据文件——换地图（改地名、价格、卡牌、格子布局）零代码；**棋盘形状本身也是数据**：移动路线由每格的 next 指针构成有向图（本棋盘 = 外环 + 机场对角支线，01 §5.1），引擎按图行走，不假设"单一环形"；② 落点结算按 `cell.type` 的处理器注册制组织（一个类型一个处理函数），新增格子类型不改动既有规则代码；③ 监狱、玩家间交易等可选机制作为**规则模块**：规格保留在 01 §8/§10，本版 `jailEnabled=false` 且不写实现代码，未来启用时按规格补实现并扩展下述类型（所需字段已在注释中标明）。

```ts
// 创建一局。randomSeed 决定洗牌与所有骰点 → 同一 seed 全局可复现（测试的关键）
function createGame(input: {
  board: BoardData; cards: CardsData; config: GameConfig;   // 来自 @richman/board-data
  players: { id: string; nickname: string }[];               // 按座次
  seed: string;
}): GameState;

// 应用一个玩家意图。成功 → 新状态 + 本次产生的事件序列；失败 → 错误码，状态不变
function applyIntent(state: GameState, playerId: string, intent: Intent):
  | { ok: true; state: GameState; events: GameEvent[] }
  | { ok: false; code: ErrorCode };
```

### 4.1 核心状态类型（`types.ts`，字段名以此为准）

```ts
interface GameState {
  seed: string;                    // 随机数状态（掷骰、洗牌都从它推进）
  turn: number;                    // 第几回合（每位玩家行动一次算一回合）
  phase: 'playing' | 'game_over';
  turnPhase: 'awaiting_roll' | 'awaiting_buy_decision'
           | 'awaiting_build_decision' | 'managing';   // 与 01 §4 状态机一致（无双数加掷；监狱模块启用时增加 'awaiting_jail_decision'）
  currentPlayerId: string;
  players: PlayerState[];          // 座次顺序
  properties: Record<number, PropertyState>;  // cellId → 产权状态
  decks: { chance: string[]; destiny: string[] };  // 卡 id 队列，抽顶补底
  debt: DebtState | null;          // 债务状态（01 §11），非空时冻结正常流程；同一时刻仅一笔，多笔应付按座次顺序逐笔进入（01 §13 E15）
  // 本版无 pendingTrade 字段：玩家间交易模块关闭（01 §10）；未来启用时扩展
  lastDice: [number, number] | null;
  recentLog: GameEvent[];          // 最近 200 条事件（供重连/刷新后重建日志面板，§7）
  winnerId: string | null;
}
interface PlayerState {
  id: string; nickname: string;
  color: 'red' | 'blue' | 'yellow' | 'green';   // 按座次分配
  isBot: boolean;                               // 电脑玩家（§4.4）；规则层面与真人无任何区别
  cash: number; position: number;               // position = cellId（外环或支线上的任意格）
  skipTurns: number;                            // "暂停 N 回合"效果的剩余回合数（01 §9 skip_turn）
  // 本版无监狱字段：模块关闭（01 §8）；未来启用时扩展 inJail / jailAttempts / jailCards

  bankrupt: boolean;
  bankruptTurn: number | null;                  // 出局回合；未破产为 null（01 §12 结算展示）
  online: boolean;                              // online 由服务器层维护
}
interface PropertyState { ownerId: string | null; level: number; mortgaged: boolean; }
interface DebtState { debtorId: string; creditorId: string | null /* null=银行 */; amount: number; }
```

### 4.3 事件枚举（GameEvent，客户端动画与日志的驱动源）

每个事件含 `type` + 所需字段；客户端按顺序播放动画，全部播完后界面应与快照一致。

`game_started` · `turn_started {playerId}` · `dice_rolled {playerId, dice}` · `token_moved {playerId, path[]}`（逐格路径，供跳格动画）· `salary_collected {playerId, amount}` · `property_bought {playerId, cellId, price}` · `buy_declined` · `rent_paid {from, to, cellId, amount}` · `tax_paid {playerId, amount}` · `card_drawn {playerId, deck, cardId}` · `house_built {cellId, level, amount}`（level=5 即旅馆落成；amount 为本次实付房费，免费升级模块为 0）· `house_sold {cellId, level}` · `property_sold {playerId, cellId, amount}`（卖地回银行，变无主）· `bank_paid {playerId, amount}`（玩家实付给银行：卡牌 pay_bank / repairs）· `bank_received {playerId, amount}`（玩家从银行实收：卡牌 receive_bank）· `payment_made {from, to, amount}`（排队付款到账；`to=null` 表示银行）· `mortgaged / redeemed {cellId}`（阶段 3）· `debt_entered {debtorId, amount, creditorId}` · `debt_resolved {amount, creditorId}` · `player_bankrupt {playerId, creditorId, transferredCash}` · `turn_ended {playerId}` · `game_over {winnerId, reason: 'last_standing' | 'cash_goal'}`

> 未来模块保留事件（本版不产生）：`sent_to_jail` / `jail_roll_failed` / `jail_exited`（监狱）、`trade_proposed` / `trade_resolved`（交易）。

### 4.4 电脑玩家（Bot）

电脑玩家**不是**引擎里的特殊逻辑，而是一个"自动产生 intent 的普通玩家"——规则、校验、事件与真人完全一致（`PlayerState.isBot` 仅供 UI 标识与驱动层识别）。

- **决策函数**：`packages/engine/src/bot.ts` 导出 `chooseBotIntent(state, playerId): Intent`，纯函数；随机性从 `state.seed` 派生（同局面同选择，可测试可复现）。
- **策略 v1**（单一难度，阈值集中为常量，作为未来难度档的预留参数）：
  - `awaiting_roll` → 掷骰；
  - `awaiting_airport_roll` → 再掷一颗机场支线骰；
  - `awaiting_buy_decision` → 现金 ≥ 地价 + 2000 则买，否则放弃；
  - `awaiting_build_decision` → 现金 ≥ 建筑费 + 2000 则盖，否则跳过；
  - `managing` → 直接结束回合（v1 不主动卖产）；
  - 债务状态 → 先逐幢卖房（最便宜的先卖），再抵押无房未抵押地产（抵押额最低的先抵押），再逐块卖地（最便宜的先卖），凑够即付；全部变现仍不足 → 宣告破产。
- **驱动方式**：轮到 bot 时由宿主依次调用决策函数并施加 intent，两个动作间隔 0.8~1.6 秒（让真人看清动画）——阶段 1 宿主是客户端 `LocalSession` 的定时器，阶段 2 起宿主是服务器房间。
- **合法性保证**：属性测试——任意可达状态下 `chooseBotIntent` 的产出必须被 `applyIntent` 接受（复用随机自弈仿真的骨架，04 §M2）。
- bot 永不掉线，无 resume、无托管；房间无真人在线超时回收规则照常适用。

## 5. Socket.IO 协议（阶段 2 实现）

### 5.1 客户端 → 服务器（全部使用 ack 回执）

| 事件 | 载荷 | 成功回执 | 失败回执 |
|---|---|---|---|
| `room:create` | `{nickname, requestId}` | `{ok, roomCode, playerId, token, room}` | `{ok:false, code, message}` |
| `room:join` | `{roomCode, nickname, requestId, role:'player'\|'spectator'}` | `{ok, playerId, token, room, snapshot?}` | 同上 |
| `session:resume` | `{roomCode, playerId, token}` | `{ok, room, snapshot?}` | 同上 |
| `room:add_bot` | —（仅房主，大厅中，真人+电脑 <6 时可用） | `{ok}` | 同上 |
| `room:remove_bot` | `{playerId}`（仅房主，大厅中） | `{ok}` | 同上 |
| `room:start` | —（仅房主，总玩家 ≥2 且真人 ≥1） | `{ok}` | 同上 |
| `room:leave` | — | `{ok}` | — |
| `game:intent` | `{intent}`（§4.2） | `{ok}` | `{ok:false, code, message}` |
| `room:skip_offline_turn` | —（仅房主，见 §6.3） | `{ok}` | 同上 |

`room:create` / `room:join` 的 `requestId` 是客户端生成并在 ack 前持久化的至少 128 bit 高熵幂等键；同一 operation、requestId 和规范化 payload 的重试必须返回原始成功结果（包括同一 token），不能重复创建房间或玩家。服务器把该键作为房间/玩家私有字段保存到对应对象被回收为止，不向房间广播；相同 requestId 配不同 payload 返回安全失败。`game:intent` 成功时，服务器先向房间广播本次 transition 的**一个** `game:events` 批次和紧随其后的**一个** `game:snapshot`，再调用成功 ack；客户端不得把 ack 当作事件已送达的信号。`room:skip_offline_turn` 成功 ack 仅确认已安排后续托管，并在未来定时器触发 transition 前返回；该请求本身不广播游戏事件或快照。失败不广播，统一回 `{ok:false, code, message}`，状态不变。

### 5.2 服务器 → 客户端（广播）

| 事件 | 载荷 | 时机 |
|---|---|---|
| `room:state` | `{roomCode, status, hostId, players[], takeoverPlayerId}` | 大厅内任何变化；开局时广播 `status:'playing'`；游戏中房主因离线移交、离线托管被安排或托管清除时也会广播；`takeoverPlayerId` 无托管时为 `null` |
| `game:snapshot` | `{state: PublicGameSnapshot}` | 开局，以及每个真人、BOT 或离线托管 transition 的 `game:events` 之后；进入 `ended` 时同样发送；`session:resume` 在其 ack 的 `snapshot?` 字段中返回，而非向房间广播 |
| `game:events` | `{events: GameEvent[]}` | 每个被接受的 `game:intent` transition 恰好一个批次，随后恰好一个 `game:snapshot`，二者都先于成功 ack；`room:skip_offline_turn` 的成功 ack 仅安排后续自动化，每次后续自动 transition 独立广播恰好一个事件批次和一个快照 |
| `player:connection` | `{playerId, online}` | 游戏中连接状态发生变化；大厅断线宽限期内也用于增量提示 |
| `room:closed` | `{reason: 'empty_lobby' | 'lobby_idle_timeout'}` | 大厅全员离开或断线宽限期结束后房间解散 |

`PublicGameSnapshot` 是 `GameState` 去除 `seed` 与 `decks` 队列后的公开投影，并以 `deckCounts: {chance, destiny}` 表示两副剩余牌数；静态 `cards` 数据仍保留，抽牌事件使用 `card_drawn`。开局、每个 transition、最终结算与 resume 都通过同一投影输出，不泄露随机种子或牌堆顺序。客户端不执行规则推进，必须依赖每个 transition 的快照得到新的现金、产权和阶段。

### 5.3 错误码

房间/会话错误码：`ROOM_NOT_FOUND` · `ROOM_FULL`（>4）· `GAME_ALREADY_STARTED` · `NICKNAME_TAKEN` · `INVALID_NICKNAME` · `INVALID_TOKEN` · `NOT_ENOUGH_PLAYERS` · `INVALID_ROOM_ACTION` · `NOT_HOST`。引擎错误码固定为四个：`NOT_YOUR_TURN` · `WRONG_PHASE` · `INSUFFICIENT_FUNDS` · `ILLEGAL_INTENT`（参数不合法，如对不可盖房的格子盖房）。所有失败 ack 共用 `{ok:false, code, message}`；客户端对每个码有对应中文提示文案。

## 6. 房间与会话

### 6.1 房间生命周期

- `room:create` → 客户端先持久化 `{operation:'create', requestId, nickname}`，服务器生成 **4 位数字房间码**（避开已占用）、创建者为房主并进入 `lobby`；若 ack 丢失，客户端使用相同 requestId 和 payload 重试并取回同一房间、玩家与 token；
- `room:join` → 客户端先持久化 `{operation:'join', requestId, roomCode, nickname, role}`；若 ack 丢失，使用相同 requestId 和 payload 重试并取回同一座位与 token；同一 requestId 不允许更换角色。
- **邀请链接**：`网址?room=房间码` 的形式，打开后自动跳到加入页并填好房间码（只需输昵称）——这是“分享即入局”的主要入口，大厅提供复制链接与二维码按钮；链接和 QR 只编码规范房间 URL，不含 token、playerId、requestId 或昵称；
- `lobby`：参赛者加入（真人+电脑合计 ≤6，昵称去重）、离开；房主可添加/移除电脑玩家（按可用昵称自动命名，避开观众重名）；房主 `room:start` 后进入 `playing`，**座次由开局自动掷骰点数排序决定**（01 §3）；
  - `room:start` 校验清单（服务器 + UI 侧双重）：总玩家 ≥2 且真人 ≥1；若开启现金目标房规，**金额必须大于初始资金**（UI 侧输入框即时拦截，服务器侧 `createGame` 也会抛错兜底，01 §12）；
- `playing`：游戏进行，玩家离开不移除，仅标记离线；
- `ended`：`game_over` 后停留在结算画面，1 小时后房间回收；
- 空房（lobby 全员离开）立即回收；`playing` 中的房间若全员离线超过 24 小时回收（存档保留，见 §7）。

### 6.2 会话与断线重连

- 建房/加入首次 emit 前，客户端将 pending requestId 与规范化表单 payload 存入本地；成功 ack 后原子写入 `{roomCode, playerId, token}`（键 `richman_session`）并删除 pending。token 为服务器生成的随机串，是重连凭证。
- 建房/加入 ack 超时是“结果不明确”，不能假定服务器未执行；刷新、断线或重试必须复用同一 pending requestId，取回原始成功结果。
- 断线（刷新、切后台、网络抖动）后重新打开页面 → 客户端发现本地有会话 → 自动 `session:resume` → 校验 token → 总是返回公开 `room`（包含 `takeoverPlayerId`），`playing` 或 `ended` 房间另带 `snapshot?`，直接恢复对应牌局或结算状态。
- Socket.IO 自身的短暂重连后也必须执行 resume 重新绑定新 socket；不能只把 transport reconnect 当成房间身份恢复。

### 6.3 轮到离线玩家时

- 默认**等待**：界面向所有人展示“等待 ×× 回来（离线）”。
- 仅当权威状态 `debt === null`、当前行动者为离线真人、请求者为在线房主且没有现有自动化时，房主可选择 `room:skip_offline_turn` **托管本回合**；离线债务人必须自己重连处理资产，不显示托管按钮。
- 托管安排成功后，`PublicRoomState.takeoverPlayerId` 设为该玩家并通过 `room:state` 广播；resume 也必须返回该锁。该玩家即使重连仍不能手动行动，直到服务器完成/终止托管并清除字段、再次广播 `room:state`。
- 托管自动执行正常掷骰移动结算、无主地一律不买、自己地一律不盖、`managing` 直接结束回合；若自动结算产生无法自动偿付的债务，托管中止并清除锁，恢复等待该玩家处理债务。
- 电脑玩家永不离线，不适用本节（由服务器按 §4.4 自动驱动）。
- 观战者使用独立 `PublicRoomState.spectators` 名单，上限 3，不进入引擎 `players`、回合、破产或房主转移。可以在 lobby/playing/ended 加入；中途加入和重连返回同样的公开快照，不包含随机种子或牌堆顺序。
- `playerId` 会话字段标识认证成员；是否参赛由服务端成员集合决定，不能通过请求自行更换身份。观众的游戏意图、房间管理和离线托管请求全部拒绝；只允许读取、恢复自身连接和离开。
- 观战断线保留 5 分钟，重连恢复原观战身份；到期或主动离开释放观战席。开局不取消观战倒计时，观众不阻止空大厅回收。客户端缺少 role 的旧待加入请求清除后重新发起，不默认为另一身份。

## 7. 存档与恢复

- 每个被接受的 intent 处理完后，将 `{room 元数据, GameState}` 全量写入 `apps/server/saves/<roomCode>.json`（原子写：先写临时文件再改名）。
- 服务器启动时扫描 `saves/`，恢复所有 `playing` 状态的房间（全员标记离线，等玩家 resume 回来）。→ **服务器重启/崩溃不丢牌局**。
- `ended` 的存档在房间回收时删除。GameState 里不含事件全史（日志仅保留最近 200 条用于回放显示），存档体积无忧。

## 8. 安全与边界（内部使用的合理简化）

- 信任模型：拿到房间码的人即可加入——内部亲友玩法，不设防。服务器仍**校验一切 intent 合法性**（§3），作弊在协议层不可能。
- token 只防"冒充重连"，不做加密身份体系。
- 生产环境同源部署（静态页与 Socket.IO 同端口），无需处理跨域；开发环境用 Vite 代理。
- 不收集任何个人数据；日志仅进程内，含昵称与操作，不含设备信息。
