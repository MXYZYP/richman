# 附 · 多地图框架交付说明

> 适用提交：`ed2ce86 feat: add multi-map gameplay and local recovery`  
> 目的：补充 `plan/05-阶段2-联机版.md` 未覆盖的多地图、版本化地图包与规则模块注册表交付说明，供合并决策使用。

## 第一部分：给 owner 的通俗版

### 1. 来源：这是 owner 批准的后续功能，不是 M3 实现过程中的自主扩张

多地图框架不是为了完成 M3 联机客户端而由实现者自行加入的功能。M3 基线完成后，owner 已批准独立的多地图设计和实施计划；交接说明将后续顺序明确为：

1. bot 主动赎回；
2. 多地图模块化；
3. 本机两槽断点续玩。

owner 随后要求“按照顺序实现”，因此多地图属于明确授权的后续产品工作。

造成终审疑问的原因是交付组织不清晰：多地图、bot 赎回和本机存档被合并进同一个 `ed2ce86` 提交，并继续留在名为 `m3-client-online` 的分支中。它没有被登记到原始 `plan/05`，从分支名和提交边界看，确实容易被理解为 M3 的范围扩张。这是文档和提交拆分上的缺陷，不应反过来描述成多地图原本就在 M3 计划内。

### 2. 动机：它解决的是紧接 M3 的第二张地图需求，不是 M3 联机本身

如果目标严格限定为“让中国之旅支持本地和联机游玩”，多地图不是必需条件。原来的固定 `board.json + cards.json + game-config.json` 足以支持一张地图，服务器也可以继续只创建中国之旅。

引入框架时需要解决的实际问题，是 owner 已经确定下一阶段要增加新地图。没有统一地图包时，第二张地图会迫使项目在以下两种不良方案中选择：

- 复制一套 engine、server、client，再维护两套规则；
- 继续在共享代码中按地图名称和格子 ID 添加条件分支。

多地图框架把棋盘、卡牌、配置、展示坐标和所需规则版本组合为一份不可变 `MapPack`，使本地模式、bot、联机房间和客户端展示继续共享同一套 engine。

本机两槽存档也从精确地图身份中获益：恢复时可以确认存档依赖的地图版本仍然存在。但这一点单独使用简单的 save schema 或 build version 也能解决，不能把存档兼容性当作引入整套多地图框架的唯一理由。

结论：**多地图不是 M3 联机的必要改动；它是为已经排入下一阶段的第二张地图提前完成的基础设施。** 在当前提交尚未包含第二张正式地图时，这部分用户价值还没有完全兑现。

### 3. 现状：目前只有一张正式可玩地图

当前 production registry 的 active catalog 只有：

- `china-tour@1`：正式地图，玩家可选择并游玩。

仓库中的 `packages/board-data/maps/__test__/test-map-v1` 是永久测试 fixture，用于证明共享代码没有把中国之旅的格子数量、名称、ID 连续性和布局写死。它不会出现在玩家地图列表中，也不能算作第二张正式地图。

“世界之旅”目前只有已批准的设计资料，尚未作为 `world-tour@1` 注册或发布。因此当前状态应准确表述为：

- 多地图基础设施已经运行；
- 第二张正式地图尚未交付；
- 现有玩家仍只能玩中国之旅。

### 4. 必要性对照：如果维持单张固定棋盘，可以少掉什么

如果 owner 决定本版以及近期都只保留中国之旅，可以移除下列整套能力：

| 可移除部分 | 单图替代方案 |
|---|---|
| `MapPack`、manifest、地图 catalog/registry、exact `MapRef` | 直接导入固定的 board/cards/config |
| canonical hash 和通用 `mapValidation` | 保留原有中国之旅专项数据校验 |
| test-map 及跨包验证链 | 删除；单图不需要证明通用性 |
| `RuleModuleRegistry` 和 module effect/intent/event envelope | engine 直接执行原有 core switch |
| `createGame` 的 `mapRef`、`ruleModules` 参数 | `createGame` 固定使用中国之旅规则 |
| `room:create.mapId` 和房间 exact map 锁定 | 房间始终创建中国之旅 |
| 客户端地图 selector、resolver、资源 allowlist | 固定加载中国之旅资源 |
| 数据化通用棋盘 presentation | 保留中国之旅原有固定布局 |
| 存档的 exact map resolution | 使用 save schema/build version 判断兼容性 |

- 约 1,000–2,000 行与当前存档、兼容检查和通用硬化存在重叠价值；

这是按职责拆分的估算，不是可以由 Git 精确切割的数字，因为多个文件同时实现了多地图、本机存档和 M3 session 适配。

owner 的取舍可以简化为：

- **近期确定会上第二张地图**：现在保留可避免以后再次横切 engine/server/client；
- **长期只玩中国之旅**：整套框架明显偏重，移除后维护面会更小。

### 5. 对引擎和服务器的改动分别有什么用

#### `RuleModuleRegistry`

它是编译进正式版本的受控分发层，不是允许运行时安装第三方插件的插件系统。

地图必须声明所需 module，例如当前中国之旅声明 `core@1`。registry 负责：

- 确认 module 存在且版本准确；
- 按 effect、intent 或 cell type 找到唯一 handler；
- 拒绝未知 module、重复注册和 handler 冲突；
- 让未来地图增加新机制时不复制 engine，也不把地图规则放到客户端执行。

当前抽卡、移动和结算的 core 实现没有被改写，只是在入口处通过 registry 分发。因此对只有 `core@1` 的中国之旅而言，它主要增加了一层间接调用。

#### `createGame(..., mapRef, ruleModules)`

新增必填参数的目的，是把“这局使用哪一版地图、哪一版规则”写入确定性 `GameState`，而不是依赖进程当前的全局默认值。

这样本地游戏、server 房间、bot、重连、模拟和存档恢复都必须使用同一组身份；旧存档也不能在找不到原版本时悄悄换成 active/latest 地图。对固定单图项目而言，这些参数是冗余的，可以由一个全局常量代替。

#### 内容哈希

`MapRef` 由 `id + version + contentHash` 组成。hash 覆盖地图 metadata、棋盘、卡牌、配置、规则 module 引用和 presentation，用来区分“名称和版本号相同，但实际内容已经不同”的情况。

它主要服务：

- 存档恢复时精确匹配地图内容；
- 联机房间锁定创建时的准确地图引用；
- 客户端收到快照后确认本地具有完全一致的地图包；
- 内容不匹配时明确拒绝，而不是 fallback 到另一版本。

它**不是防篡改签名**。能够修改程序或地图文件的人也可以重新计算 hash。联机公平仍由 server authoritative 保证：骰子、移动、抽卡和结算只在服务器 engine 中执行。hash 是版本身份与兼容性机制，不是安全认证机制。

### 6. 风险与回退：可剥离，但不是“删几个文件”

当前多地图引用已经横跨 `board-data → engine → protocol/server → client/save`。静态搜索可见约 31 个 production 文件直接引用 `MapPack`、`mapRef`、`ruleModules`、registry 或地图解析接口；相关测试文件更多。

因此不能只删除 manifest、registry 和 test-map。完整回退至少需要：

1. 恢复固定中国之旅数据入口；
2. 从 `GameState`、`createGame` 和 hydrate 移除地图/module 身份；
3. 将 effect、intent、bot 分发恢复为直接 core 调用；
4. 从 protocol 和 room lifecycle 移除 `mapId/mapRef`；
5. 将 client setup、resolver 和 board presentation 恢复为单图实现；
6. 把本机存档改为固定地图 + schema/build version 校验；
7. 删除或重写相应测试。

也不能直接 revert `ed2ce86`，因为该提交同时包含已交付的 bot 主动赎回和本机两槽断点续玩；整体 revert 会把这两项一起删除。

但引擎没有不可逆地重写：

- core effect 和 intent 的原有实现仍然存在；
- registry 主要包在调用入口外层；
- deterministic migration 测试证明包装前后中国之旅规则结果一致。

所以更准确的结论是：**回退技术上可行，但属于几十个文件的跨包手术，不是低成本删文件；引擎并未深度改写到无法剥离。**

如果现在回退，能够减少单图版本的长期维护面；代价是世界之旅进入实现时还要重新完成一次地图身份、展示数据化和新规则扩展边界的改造。

## 第二部分：技术交付清单

### `@richman/board-data`

- 新增 `MapRef`、`RuleModuleRef`、`MapPack`、catalog 和 presentation 类型。
- 将中国之旅整理为 `maps/china-tour/v1`，棋盘、卡牌和 game config 内容不变。
- 新增 canonical serialization 与纯 TypeScript SHA-256 内容哈希。
- 新增 exact map registry：active map 用于新开局，exact ref 用于恢复和重连，禁止 fuzzy fallback。
- 将校验拆成通用 map validation 与中国之旅数据源 reconciliation。
- 新增非 catalog 的 test-map，覆盖不同格子数、非连续 ID、不同标签和不同布局。

### `@richman/engine`

- `GameState` 保存 exact `mapRef`、启用的 `ruleModules` 和完整不可变 game data。
- `createGame` 必须显式接收地图与规则身份。
- 新增 `RuleModuleRegistry`、module cell/effect/intent/event envelope，以及确定性的 bot hook 顺序。
- 新增 `hydrateGameState`，只接受与已解析 `MapPack` 完全一致的浏览器输入。
- simulation、bot、movement、effects 和 intent 入口改为读取状态携带的数据或 module registry。
- deterministic migration 测试比较相同 seed 改造前后的关键状态序列。

### `@richman/protocol` 与 server

- `room:create` 增加 `mapId`；join 不允许另选地图。
- Room 在创建时由 server 解析并锁定 exact `MapRef`，开局、重连和托管期间不变。
- `PublicGameSnapshot` 改为逐字段 allowlist，并携带安全的地图身份；不发送 seed、私有牌堆、完整 board/cards/config 或 module 私有数据。
- server 开局从锁定的 MapPack 取得 board、cards、config 和 required modules。

### client

- setup 从 active catalog 生成地图选项；只有一张 active map 时隐藏 selector。
- local game 和 online room 都按 map id 开局。
- 收到 exact `MapRef` 后只解析完全匹配的本地地图包；缺少版本或 hash 不一致时显示兼容错误，不换用其他版本。
- `GameBoard`、`BoardCell`、route 和中心 decoration 改为读取 presentation 数据，不再把中国之旅布局当成共享规则。v2.5.0 已移除 `FocusedBoard` 与局部 route window，仅保留全局棋盘。
- 地图资源只允许访问 manifest 声明并经构建登记的 package-local assets。
- 本机两槽存档使用 exact MapRef 恢复；找不到原地图时标为 incompatible，不把浏览器 localStorage 当作可信状态。

### 专项测试覆盖

- canonical serialization、SHA-256 标准向量、字段或数组顺序变化与非法 JSON 值。
- map identity、content hash、graph、cell reference、presentation 覆盖、坐标、资源 allowlist、未知 module 和无效地图。
- active/exact registry resolution、重复版本和 stale hash。
- test-map 贯穿 board-data、engine、server/protocol 和 client rendering。
- module 注册冲突、module envelope 隔离、稳定执行顺序和非法 intent。
- 相同 seed 下的 dice、抽卡、移动和结算确定性回归。
- server 房间地图锁定、创建/加入/开始/重连、公开快照边界。
- client selector、exact resolver、动态棋盘、focused route、兼容错误和本机存档恢复。
