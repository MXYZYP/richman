## 1. 关键设计约束

- **引擎零改动**：`@richman/engine` 原样在服务器上运行。若联机改造中发现引擎需要改，先停下来想清楚是不是违反了 03 §4 的纯函数约定，并记录偏差。
- **客户端双模式**：抽象一个 `GameSession` 接口（提供：发 intent、订阅事件流、读快照），两个实现——`LocalSession`（阶段 1 的本地引擎，保留为"本机同乐"入口，作为免费的回归测试工具）与 `OnlineSession`（Socket.IO）。游戏界面组件只依赖该接口，两种模式共用全部 UI。
- 客户端收到 `game:events` 先排队播动画，播完后用状态校对；任何时刻收到 `game:snapshot` 以快照为准强制对齐。

## 2. 里程碑与任务分解

### M1 · 服务器骨架与房间系统

- [x] `apps/server`：Node 20 + Socket.IO 入口；生产模式托管 client 构建产物（单端口 :3000，03 §2）
- [x] 房间管理器：创建（4 位数字房间码防撞）、加入（真人+电脑合计 ≤4、昵称去重）、离开、房主移交（房主离开大厅时顺延）、添加/移除电脑玩家（仅房主）、开始（总玩家 ≥2 且真人 ≥1）；全套 M1 `room:*` 协议与错误码（03 §5、§6.1）
- [x] token 生成与校验（03 §6.2）
- [x] `pnpm party` 聚会脚本：构建 + 启动 + 终端打印局域网地址与二维码（规格见 07 号文档 §A1，属本阶段交付物）
- **M1 验证（2026-07-10）**：房间管理器、真实 Socket.IO 客户端、同端口静态托管、production bootstrap 与 LAN 地址选择均有 Vitest 覆盖；完整测试/typecheck/data/build gate 与真实 launcher smoke 见本里程碑交付记录。M1 只实现房间层，未接入 `GameState`、`game:*`、持久化或客户端大厅。

### M2 · 服务器引擎接入与状态广播（完成）

- [x] 每个房间持有一个 `GameState`；`room:start` 时用 `createGame` 开局，seed 由生产服务随机生成并固定在状态中
- [x] `game:intent` → 校验发送者是该 playerId → `applyIntent` → 成功：先广播一个 `game:events` 批次（需要时再发快照）后 ack `{ok}`；失败：仅以共享失败 ack 返回错误码
- [x] `turn_ended` 或游戏结束后追发 `game:snapshot` 兜底同步；`ended` 房间保留结算状态并允许 token resume
- [x] 服务器驱动电脑玩家回合（03 §4.4：轮到 bot 时依次施加其决策 intent，间隔 0.8~1.6 秒）
- **验证**：Vitest 的两个 Socket.IO 测试客户端覆盖"建房→加入→开局→掷骰→广播一致"、事件先于 ack、断线 resume、`ended`、"1 真人 + 1 电脑"开局与电脑自动行动
- [x] `room:skip_offline_turn` 验证 skip 请求并安排被跳过的 player 的接管、立刻 ack；后续每个由服务器定时触发的接管 intent 独立复用共享的 transition 并独立广播，skip 请求本身不会在 ack 之前推进或广播

### M3 · 客户端 UI / `GameSession` 联机改造

- [x] `GameSession` 抽象落地；首页改为三入口：**创建房间 / 加入房间 / 本机同乐**（+ 检测到未结束会话时显示"回到上一局"）
- [x] 大厅界面：房间码大字展示（方便报号）、**复制邀请链接与邀请二维码按钮**（微信发给亲友，点开自动填好房间码，见 03 §6.1）、玩家列表（电脑玩家带机器人标识）、房主的加/减电脑玩家与开始按钮
- [x] 断线体验：顶部横幅"连接断开，正在重连…"；重新打开页面自动 `session:resume` 回局；其他玩家头像上的离线标记（`player:connection`）
- [x] 房主对离线玩家回合的"托管本回合"按钮（03 §6.3）
- **验证**：本地起服务，两个浏览器窗口手动对玩一段，全部界面状态实时一致

### M4 · 持久化、恢复与回收

- [x] 每个被接受的 intent 后原子写 `apps/server/saves/<roomCode>.json`；启动扫描恢复 `playing` 房间；`ended` 房间按 03 §6.1 回收并删档
- **验证**：Vitest：写入→杀进程（模拟）→重启→房间与状态完整恢复
- **回收归属**：M1 只清理超时 lobby；`playing` 房间“全员离线超过 24 小时回收”随本 M4 的 JSON 存档、启动恢复和删档策略一并实现。M4 前不得把进程内删除误称为可靠回收，否则会直接丢失进行中的牌局。

### M5 · 端到端验证（本阶段的重头戏）

- [x] Playwright 脚本（`pnpm e2e`，跑在生产模式单端口上）：
  1. **四人整局**：4 个浏览器上下文（其中 2 个用手机视口 390×844），建房、加入、打到有人破产、直至胜利画面，全程断言四端看到的关键状态一致（现金、位置、产权）
  2. **断线重连**：中盘强制断开一人网络 → 其余三人看到离线标记 → 该玩家重开页面 resume → 状态与其他三端一致 → 继续游戏
  3. **服务器崩溃恢复**：中盘 kill 服务器进程 → 重启 → 四端刷新回局 → 继续打完
  4. **托管回合**：一人离线且轮到他 → 房主托管 → 回合自动完成、游戏继续
  5. **人机混战**：1 名真人 + 3 个电脑玩家开局并推进若干回合，验证电脑自动行动、间隔节奏与四端状态一致
- [x] **真实设备实测**：owner 的电脑跑服务，电脑 + 至少一部手机（同 WiFi）真实对玩 15 分钟以上，记录问题
- [x] 全部问题修复后，交独立 review agent 审查

**Owner 验收清单**：

- [x] 一方彻底关掉浏览器，另一方看到其头像变离线；轮到离线者时房主能"托管"让游戏继续

- [x] 房主能在房间里加电脑玩家，开局后电脑轮到时自动掷骰行动，节奏不卡
- [x] 用"本机同乐"入口还能像阶段 1 一样单机热座玩
