## 第一部分：给 owner 的通俗版

### 先给结论

1. 多地图是 owner 在 M3 基线完成后明确批准的后续产品方向，不是实现者写联机客户端时自行加出的需求。
2. 它不属于原始 M3，也没有解决当时中国之旅联机的阻塞；原始单图方案本来就能完成 M3。
3. 当前 production 仍只有一张正式地图：`china-tour@1`。`test-map-v1` 只供自动测试使用，不会出现在玩家地图列表。
4. `ed2ce86` 的 16,902 行新增不能全部叫“多地图代码”。按文件主职责保守归类，明确属于多地图的是 92 个文件、11,045 行新增；其中 runtime / production / config 约 4,039 行，其余主要是测试、manifest 和设计文档。
5. 若只判断“原始 M3 联机版需要多少”，答案是：多地图专属代码 **0 行是必需条件**。这 11,045 行的绝大多数价值要到第二张正式地图交付后才兑现。
6. 可以回退到单图，但不是删几个文件。地图身份已经贯穿 board-data、engine、protocol/server、client 和存档；需要跨包重构。好消息是原 core 规则仍在，注册表主要包在入口外层，并非不可剥离。

### 1. 来源：谁提出，为什么开始做

仓库中的产品交接记录 `docs/handoffs/2026-07-15-codex-continuation-handoff.md` §2.3、§2.6 记载：

- M3 基线完成后，owner 认为“中国之旅”现阶段可以先告一段落；

- owner 选择继续按“bot 主动赎回 → 多地图模块化 → 本机两槽断点续玩”的顺序实施。

随后形成并获准实施的技术资料是：

- `docs/superpowers/specs/2026-07-15-multi-map-modularization-design.md`；
- `docs/superpowers/plans/2026-07-15-multi-map-modularization.md`。

因此需要区分两件事：

- **产品方向来源**：owner 明确授权；
- **具体架构选择**：实现者根据该方向设计了 `MapPack`、registry、hash、`RuleModuleRegistry` 等机制。

终审会产生疑问，是因为这项后续工作仍留在 `m3-client-online` 分支，并与 bot 赎回、本机存档一起进入同一个 `ed2ce86` 提交；原始 `plan/05` 也没有登记这项扩展。分支名、提交边界和正式计划没有准确表达范围，这是交付组织问题。多地图既不能被追溯性地说成原始 M3，也不能被说成未经 owner 授权。

### 2. 动机：它解决了什么当下问题

严格回答：**它没有解决 M3 联机客户端当时的实际故障或阻塞。**

若产品当时只要求“中国之旅支持本地和联机”，原来的固定 `board.json + cards.json + game-config.json` 已经够用，server 始终创建中国之旅即可。原始 `plan/05-阶段2-联机版.md` §1 还明确写了“引擎零改动”。

引入框架的真实动机，是 M3 基线之后已经批准了“以后增加新地图和少量新机制”的下一阶段方向。没有公共框架，真正开始第二张地图时通常只能：

1. 复制一套 engine/server/client，形成两套长期分叉；或
2. 在共享代码里不断增加“如果是某地图 / 某格子 ID”的特殊判断。

当前方案把每张地图的棋盘、卡牌、配置、展示坐标、主题和所需规则版本装进一个不可变 `MapPack`，本地游戏、bot、联机房间和 UI 继续共用同一套程序。

本机存档确实也从 exact `MapRef` 获益：恢复时能确认原地图内容仍存在。但单图项目用 save schema 或 build version 也能完成兼容检查，所以存档不是引入整套多地图框架的充分理由。

结论：这是**经授权但提前建设的下一阶段基础设施**。在第二张正式地图上线前，主要收益是降低未来接图风险，不是给当前中国之旅增加可见玩法。

### 4. 必要性对照：维持原单图，会少掉哪些复杂度

| 当前多地图能力 | 单图版本怎么做 | 单图可少掉的维护面 |
|---|---|---|
| `MapPack`、manifest、catalog、registry | 固定导入中国之旅 board/cards/config | 不再维护地图发现、active/exact 两套解析 |
| `MapRef = id + version + contentHash` | 用常量表示“中国之旅” | GameState、协议、房间和存档不再传地图身份 |
| canonical stringify + SHA-256 | 不需要内容指纹 | 删除 canonical JSON 边界和 hash 测试 |
| 通用 `mapValidation` | 保留中国之旅专项校验 | 不再验证任意拓扑、presentation、资源 allowlist、module 引用 |
| `RuleModuleRegistry` | engine 直接执行原 core switch | 少一层 handler 注册、冲突检查和 module envelope |
| `createGame` 必填 `mapRef/ruleModules` | 固定使用 core 规则 | 所有调用者和测试不再传两组身份参数 |
| `room:create.mapId`、房间锁图 | 房间固定中国之旅 | protocol/server 不再处理地图选择和 exact resolution |
| client catalog/resolver/assets | 直接加载中国之旅 | 不再处理版本缺失、hash 不符和地图资源登记 |
| 数据化通用棋盘 presentation | 保留原中国之旅固定布局 | UI 不再承担任意地图坐标和路线窗口 |
| test-map 跨包验证 | 删除 | 不再维护第二条测试地图全链路 |
| 存档 exact map hydration | fixed-map + save schema/build version | 恢复逻辑更短，但仍保留浏览器输入不可信校验 |

### 5. 引擎和服务器为何要这样改

#### `RuleModuleRegistry`

它不是运行时下载第三方代码的插件市场。所有 module 都随正式程序编译、审核和发布。

当前每张地图声明需要哪些规则 module，例如中国之旅声明 `core@1`。registry 负责：

- 确认 module ID 和版本存在；
- 为 cell settlement、card effect、player intent 和 bot hook 找到唯一 handler；
- 拒绝未知 module、重复 module、handler 冲突和未启用的 module envelope；
- 以稳定顺序运行启用的 hook，保持相同 seed 可复现。

中国之旅目前只使用 `core@1`。原抽卡、移动、买地和结算实现仍在，只是入口先经过 registry 再进入原 core 逻辑。对当前单图而言，这主要是一层间接调用；它的实际扩展价值要到某张地图确实需要额外正式规则 module 时才出现。

#### `createGame` 新增必填 `mapRef` 和 `ruleModules`

作用是把“这局到底使用哪份地图内容、哪组规则版本”写进 `GameState`：

- `mapRef` 固定地图 ID、版本和内容 hash；
- `ruleModules` 固定该局启用的规则 module 集合；
- 本地开局、server 开局、bot、simulation、重连和存档恢复必须携带同一身份；
- 不能因为 registry 后来切换 active 版本，就让进行中的房间或旧存档悄悄使用另一份内容。

在固定单图项目里，这两个参数可以由全局中国之旅常量替代，所以它们不是 M3 必需 API。

#### 内容哈希 `contentHash`

hash 覆盖 map metadata、board、cards、config、required modules 和 presentation；`MapRef` 使用 `id + version + contentHash` 精确识别内容。

它的主要用途是：

1. **联机对局一致性**：server 在创建房间时锁定 exact MapRef；开局时再次按 exact ref 取包。client 只渲染本地完全匹配的地图包。
2. **存档兼容性**：恢复时找不到原版本或 hash 不同就拒绝，不拿 active/latest 地图顶替。
3. **版本发布纪律**：同一 ID、同一 version 下内容被改动时，hash 会暴露差异。

它不做两件事：

- **不是防篡改签名**：能修改程序和地图文件的人也能重算 hash；它没有私钥签名或信任链。
- **不是自动版本迁移**：遇到旧 hash 时当前策略是拒绝恢复/渲染，不会自动把旧局升级成新地图。

联机公平仍依赖 server authoritative：骰子、移动、抽卡和结算只由 server engine 决定。hash 是内容身份和兼容校验，不是反作弊机制。

### 6. 风险与回退：能否先撤掉多地图

#### 结论

**能回退，但不是“删几个文件”；属于跨包、有边界但不小的重构。**

当前静态核查有约 31 个 production 文件直接引用 `MapPack`、`MapRef`、`mapRef`、`ruleModules`、registry 或 exact map resolver；按文件主职责明确属于多地图的改动覆盖 92 个文件，测试调用点更多。

不能直接整体 revert `ed2ce86`，因为该提交还混入 bot 主动赎回、本机两槽断点续玩和其他交付内容。整体 revert 会一并丢掉它们。

选择性回退至少要：

1. 恢复固定的中国之旅 board/cards/config 导出；
2. 从 `GameState`、`createGame`、hydrate 和所有调用点移除地图/module 身份；
3. 将 intent、effect、cell settlement 和 bot hook 恢复为直接 core 分发；
4. 从 protocol、room create、room state、public snapshot 和 server start lifecycle 移除地图选择/锁定；
5. 将 client setup、resolver、assets、board layout 和 focused route 恢复成单图实现；
6. 把本机存档改成固定地图 + save schema/build version 兼容校验；
7. 删除 test-map 和通用框架测试，恢复单图测试期望。

但它没有不可逆地改写引擎：

- core effect/intent 代码仍然存在；
- registry 主要包在调用入口；
- 中国之旅数据仍完整；
- 已有确定性迁移测试可作为回退前后的行为对照。

因此风险主要是**横跨层级、调用点多，容易漏掉存档或协议兼容边界**，而不是规则已经混成无法分离。若决定回退，应单独开一个回退切片，保留 public snapshot allowlist 和浏览器输入校验，不能用删除目录代替完整迁移。

### C. `@richman/protocol` 与 `@richman/server`

- `room:create` payload 新增 `mapId`；join 不能另选地图。
- public room state 携带 map summary；public game snapshot 携带 exact `mapRef`。
- `PublicGameSnapshot` 从 `Omit<GameState, ...>` 改为逐字段 allowlist：
  - 允许公开 turn、players、properties、debt、dice、winner、cash goal、recent events、deck counts、mapRef；
  - 不发送 seed、私有牌序、完整 board/cards/config 和 module 私有状态。
- `RoomManager` 创建房间时解析 active map 并锁定 exact ref；开局时按 exact ref 重新解析，不使用后来变更的 active/latest。
- server game runtime 从锁定 MapPack 取得 board、cards、config、mapRef 和 required modules 后调用 engine。

### D. `@richman/client`

- setup 从 active catalog 生成地图选项；只有一个 active map 时隐藏 selector。
- local 与 online create flow 都携带 map ID / exact ref。
- `mapResolver.ts` 只接受 exact version/hash；缺失或不一致时显示兼容错误，不 fallback。
- `mapAssets.ts` 只允许构建时登记、manifest 声明的 package-local asset。
- `GameBoard.vue`、`BoardCell.vue`、`boardLayout.ts` 改为读取 MapPresentation（v2.5.0 已删除局部视图的 `FocusedBoard.vue` 与 `focusedRoute.ts`）：
  - 不固定 14×14；
  - 不固定 61 格；
  - route、branch 和 center decoration 由地图数据决定；mobile focused window 随局部棋盘一并移除。
- 本机存档保存 exact MapRef；恢复前用 exact pack hydrate，不信任 localStorage 里的 board/cards/config。

### E. 测试覆盖清单

本次终审说明不重复跑评审员已确认的全量 gate；这里只列已交付测试职责：

- **hash**：canonical serialization、SHA-256 标准向量、字段/数组顺序、非法 JSON 值、内容变化导致 hash 变化。
- **map validation**：schema、cell graph、start cell、引用完整性、presentation 覆盖/坐标、asset allowlist、未知 module、缺失 `core@1`、hash mismatch。
- **registry**：active/exact resolution、重复 map version、inactive map、stale hash、clone/freeze。
- **engine module**：handler 冲突、module envelope 隔离、未启用 module、稳定 hook 顺序、非法 intent。
- **deterministic migration**：相同 seed 下迁移前后 dice、抽卡、移动、结算和关键状态序列一致。
- **hydrate**：exact MapRef/modules/data 匹配，拒绝 tampered、stale、incompatible 状态。
- **server/protocol**：创建房间锁图、未知地图拒绝、join 继承房间地图、开局 exact resolution、重连和 public snapshot 边界。
- **client**：单/多地图 selector、exact resolver、asset resolution、动态棋盘、focused route、兼容错误和本机存档恢复。
- **test-map 全链路**：不同格子数、非连续 ID、不同布局的数据从 board-data 进入 engine、server 和 client rendering，证明共享代码没有依赖中国之旅常量。
