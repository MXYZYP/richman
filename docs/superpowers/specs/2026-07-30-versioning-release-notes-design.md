# 版本号与更新说明设计

日期：2026-07-30
状态：已确认设计，待实施计划

## 1. 目标

为 Richman 增加用户可见的产品版本号和完整更新历史，并保证每次 `main` 出现新的部署版本时都有对应说明。

用户已确认：

- 游戏内提供版本入口和更新说明；
- 仓库同时维护 `CHANGELOG.md`；
- 使用三段式版本号（Semantic Versioning，例如 `2.3.1`）；
- 默认每次发布递增 patch，重要功能可显式递增 minor；
- 更新说明采用玩家能直接理解的简短文案；
- 采用结构化发布清单作为唯一数据来源。

## 2. 非目标

本切片不实现：

- 依赖 GitHub Releases API 的运行时请求；
- 自动分析 commit 文案来判断 major/minor/patch；
- 自动创建 Git tag 或修改 GitHub 仓库内容的 CI 写权限；
- 为内部 workspace package 建立独立版本体系；
- 逐条还原早期内部开发提交；历史记录只补录 GitHub 可以确认的可玩里程碑。

## 3. 版本规则

根目录产品版本采用 `major.minor.patch`：

- patch：默认选择，用于一般更新和修复，例如 `2.3.0 → 2.3.1`；
- minor：重要玩家功能，例如 `2.3.1 → 2.4.0`；
- major：出现产品形态的大阶段变化时使用，例如单机版进入联机版；当前不自动触发。

每个改变玩家实际运行内容并进入 `main` 的新部署 revision，必须包含一个高于上一部署版本的新版本条目。纯文档、规划、截图和 CI 维护不产生玩家版本；对同一 commit 手动重试部署也不重复递增。

当前迁移策略基于 GitHub `main` 历史、已合并 PR、README 阶段表和 plan 文档交叉回溯。仓库没有历史 Tags 或 Releases，因此以下编号是经用户确认的补编版本，而不是恢复出来的旧标签：

## 4. 单一数据来源

新增根目录 `release-notes.json`，它是版本历史的唯一人工编辑来源。结构为：

```json
{
  "releases": [
    {
      "version": "2.4.0",
      "date": "2026-07-30",
      "title": "版本说明与更新记录",
      "changes": [
        "首页新增当前版本和更新说明入口。",
        "现在可以在游戏内查看历史版本变化。"
      ]
    }
  ]
}
```

约束：

- 最新版本排在数组首位；
- `version` 必须是合法且唯一的三段式版本号；
- 新版本必须严格高于后一条历史版本；
- `date` 使用 `YYYY-MM-DD`；
- `title` 和 `changes` 不得为空；
- `changes` 只描述玩家可观察的结果，不包含文件名、函数名或内部重构细节。

根 `package.json` 的 `version` 作为工具兼容字段，由发布命令同步为最新条目的版本。其他 private workspace package 保持自己的内部版本，不作为产品版本展示。

根目录 `CHANGELOG.md` 由 `release-notes.json` 确定性生成，不允许单独维护第二份文案。

## 5. 发布命令

新增项目脚本，提供 patch 和 minor 两种常用发布方式。命令负责一次性完成：

1. 读取并校验当前发布清单；
2. 计算下一个版本号；
3. 写入日期、标题和一条或多条玩家说明；
4. 同步根 `package.json`；
5. 重新生成 `CHANGELOG.md`；
6. 再次校验三个产物完全一致。

无说明、非法版本、重复版本或生成结果不一致时，命令必须失败且不得留下半写入状态。

发布内容仍由人或 agent 明确撰写；系统不从 commit 标题猜测玩家说明。

## 6. 游戏内体验

首页底部增加低干扰入口：

```text
v2.4.0 · 更新说明
```

点击后打开符合现有视觉规范的对话框：

- 首屏显示当前版本、日期、标题和变更列表；
- 下方按新到旧显示历史版本；
- 支持明确的关闭按钮和 `Escape` 关闭；
- 对话框打开时焦点进入对话框，关闭后返回入口按钮；
- 手机 390px 宽度下内容不横向溢出，长历史在对话框内部纵向滚动；
- 不在正在进行的棋盘上常驻版本控件，避免遮挡操作；玩家回到首页即可查看。

建议组件边界：

- `releaseCatalog`：只负责暴露经过类型约束的只读发布数据；
- `ReleaseNotesDialog`：只负责入口、对话框和可访问性；
- `HomeView`：仅负责放置入口，不自行解析版本数据。

## 7. 构建数据流

Vite 在构建时读取已提交的 `release-notes.json`，将当前版本和完整历史作为编译期常量注入客户端 bundle。

结果：

- 线上和本地预览使用同一份数据；
- 查看更新说明不需要网络请求；
- GitHub 不可访问时仍可正常查看；
- 部署产物与构建时仓库 revision 一一对应。

构建前若发布清单不合法，应直接失败，而不是在界面显示占位版本。

## 8. 部署门禁

保留 GitHub Actions 的只读 `contents: read` 权限，不由 CI 创建 tag、提交或回写版本。

部署前新增发布校验：

1. `release-notes.json` 最新版本等于根 `package.json` 版本；
2. 当前 `CHANGELOG.md` 等于从发布清单重新生成的结果；
3. 对改变实际运行内容的 `main` push，当前版本必须高于该 push 之前 revision 的版本；
4. 纯 `docs/**`、`plan/**`、截图或 CI 维护可复用当前版本，不强迫编写玩家更新说明；
5. 任一适用检查失败时，在 build 和 Cloudflare deploy 之前终止。

`workflow_dispatch` 对同一 commit 的重试复用原版本，因为代码和发布说明均未变化；它不被视为新的产品版本。

## 9. 错误处理

- 发布命令输入缺失：输出可操作的中文错误，不修改文件；
- 发布清单损坏：build、test 和 deploy gate 全部失败；
- CHANGELOG 被手改：校验失败并提示重新生成；
- package 版本未同步：校验失败并指出两个版本值；
- 游戏内数据为空：视为构建错误，不提供“未知版本”静默降级。

## 10. 验证策略

自动验证：

- Semantic Versioning 的 patch/minor 递增；
- 非法、重复、倒序和空说明拒绝；
- 发布命令成功时三个产物一致；
- 发布命令失败时文件保持原样；
- CHANGELOG 生成结果稳定；
- 首页渲染当前版本入口；
- 对话框按新到旧显示当前与历史说明；
- 关闭、Escape 和焦点恢复行为。

真实浏览器验证：

- 桌面：首页入口、打开、滚动历史、关闭；
- 390×844 手机：无横向溢出、文字可读、关闭按钮可触控；
- production build 中显示的版本与 `release-notes.json` 最新条目一致。

项目级验证继续执行：

```bash
pnpm test
pnpm typecheck
pnpm validate-data
pnpm --filter @richman/client build
```

## 11. 验收标准

- 首页可见当前版本并可打开更新说明；
- 游戏内无需联网即可查看全部已记录版本；
- 根目录存在由发布清单生成的 `CHANGELOG.md`；
- `1.0.0` 至 `2.4.0` 六个里程碑均有玩家可读说明；
- 任一改变实际运行内容的新部署 revision 若未递增版本或未写说明，CI 在部署前失败；纯文档和 CI 维护不受此限制；
- 默认 patch、显式 minor 的发布命令均经过测试；
- 桌面和手机真实浏览器验收通过；
- 不增加 GitHub 写权限，不依赖 GitHub Releases 运行时 API。
