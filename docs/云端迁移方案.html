大富翁联机游戏 · 云端迁移方案

从"本地内网穿透 + 主机开机才联机"迁移到"云端 7×24 全天候联机" · 基于 richman-main 实际代码架构分析
结论速览：你的架构本身已经高度云友好——一个 Node 进程在一个端口上同时托管前端静态资源和 Socket.IO 长连接、同源部署、无数据库、无跨域。所以迁移几乎不需要改业务代码，真正的工程量在四块：① 让进程在云上常驻且崩溃自拉起；② 把 apps/server/saves/ 的 JSON 存档放到持久化存储（否则容器/实例重启会丢档）；③ 换成固定公网地址 +（建议）HTTPS；④ 补齐公网暴露后的安全与可观测性加固。朋友级流量下，单实例足够，无需 Redis、无需数据库。
⚠ 重要更正（2026-09-17 复核代码后）：上一版报告称"服务器会把每步 intent 原子写入 apps/server/saves/<roomCode>.json 并启动扫描恢复"。经核对实际代码，该磁盘持久化尚未实现（handoff 文档第 748 行明确记载"当前 server 没有磁盘持久化；房间和 gameState 全在内存"）。因此：
  • 房间状态仅存于进程内存；服务器重启 / 崩溃 / 更新 / 容器重建都会丢失进行中的牌局，玩家需重新建房或加入。
  • 客户端虽有 session:resume 重连逻辑，但服务端无存档可恢复，重连后只能回到"无进行中牌局"状态。
  • 云迁移本身不受影响（单进程单端口模型依然适用），但"重启不丢局"不是当前事实，请勿据此向玩家承诺。
  • 若需要崩溃恢复，应按 plan/03 §7 实现 JSON 原子存档 + 启动扫描（属独立开发任务，不在本次打包/上架范围内）。

2. 云端部署方案选型与对比

四个候选方向，核心判据是：是否支持有状态长连接 WebSocket、是否需要改代码、中国玩家访问延迟、运维负担、成本。

A. 国内轻量应用服务器 推荐起步

腾讯云轻量应用服务器 / 阿里云 ECS 共享型（Ubuntu 22.04）。你跑一个 Node 进程 + pm2，系统盘即持久盘。

优点：完全可控、同源单进程零改代码、国内延迟低、成本最低、存档天然持久。
缺点：需自己管系统补丁/进程；单点故障（实例挂=全停）。

B. 国内容器/云托管 成长推荐

腾讯云 CloudBase 云托管 / 阿里云 SAE / ACK Serverless。你提交 Docker 镜像，平台跑容器、支持 WebSocket、自动扩缩、日志监控开箱即用。

优点：免运维、自动伸缩、WebSocket 原生支持、健康检查集成。
缺点：需写 Dockerfile；常驻容器有基础费用；多实例仍需 Redis Adapter 才能共享房间。

C. 海外 PaaS 仅海外玩家

Railway / Fly.io / Render。Git 推送即部署，体验好。

优点：部署极简、自动 HTTPS、全球节点。
缺点：中国访问延迟高/偶发不可达；Render 免费版会休眠（不符 7×24）；费用以美元计。

D. Serverless FaaS 不推荐

Vercel / Cloudflare Workers / 腾讯云函数 SCF。

缺点：函数实例无状态、按需启停、长连接会被回收，与你"内存态房间 + 进程内 Bot 定时器"直接冲突。要适配需彻底重构（Redis Adapter + 外部状态 + 定时唤醒），工程量远超收益。除非未来重构，否则不选。

判据A 轻量服务器B 容器云托管C 海外 PaaSD Serverless
有状态 WebSocket原生支持原生支持支持不适配
需改业务代码几乎不用写 Dockerfile小改需重构
中国访问延迟低（近区域）低高/不稳不稳
运维负担中（自管）低低最低
7×24 成本量级¥25–60/月（2C2G）常驻容器 ≈¥30–80/月≈$5–15/月看似低，但需重构
横向扩展需手动+Redis平台自动（仍要 Redis）自动天然
适合阶段现在就上用户增多后海外亲友不推荐
推荐路线：现在用 A（国内轻量服务器 + pm2） 立刻实现 7×24；当用户量/房间数明显上涨、想甩掉运维时，迁到 B（CloudBase 云托管，提交同一个 Docker 镜像）。两者都吃同一个单进程单端口镜像，迁移平滑。避开 D，谨慎用 C（除非玩家主要在海外）。

3. 分步迁移实施计划

阶段 0 · 代码侧小改动（一次性，约 1–2 小时）

  1. 显式绑定 0.0.0.0：把 production.ts 的 server.httpServer.listen(requestedPort) 改为 .listen(requestedPort, '0.0.0.0')，避免某些平台默认只绑 IPv6/localhost。
  2. 存档路径可配置：让 SAVE_DIR 环境变量覆盖默认 apps/server/saves，方便容器挂载卷到任意目录。
  3. 加健康检查：在 server.ts 的请求处理器里加 if (req.url === '/healthz') { res.writeHead(200); res.end('ok'); return; }，供 pm2/平台探活。
  4. 确认构建产出：pnpm build 应同时产出 client/dist 与 server（tsc 类型检查）。现有脚本已满足。
  5. （可选但推荐）加 Dockerfile + .dockerignore，为日后走 B 方案铺路（阶段 0 不强制）。
最小改动即可上线：只做第 1–3 步（共约 10 行代码），就能直接上 A 方案。第 4、5 步是面向未来的优化。

阶段 1 · 选平台与购买（owner 操作 + 一次性安全）

  1. 腾讯云/阿里云 → 轻量应用服务器 → 区域选离玩家近（广州/上海/北京）→ 镜像 Ubuntu 22.04 → 套餐 2C2G → 记下公网 IP 与 root 密码。
  2. 安全组放行 TCP 3000（游戏）；TCP 22 仅限你自己的 IP（或先用再收紧）。
  3. 登录后：创建普通用户 + 配置 SSH 密钥 + 禁用 root 密码登录；装 unattended-upgrades 自动打补丁。

阶段 2 · 首次部署（单进程 + pm2 守护）

# 登录（建议用普通用户 + 密钥）
ssh deploy@<公网IP>

# 装运行时
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo bash -
sudo apt-get install -y nodejs
sudo npm i -g pnpm pm2

# 取代码（私有仓库推荐）
git clone <你的私有仓库> /opt/richman
cd /opt/richman && pnpm install && pnpm build

# 常驻 + 崩溃自拉起 + 开机自启
pm2 start "pnpm start" --name richman
pm2 save && pm2 startup   # 按提示执行那行命令

# 验证
pm2 status          # 应为 online
curl http://127.0.0.1:3000/healthz   # 应返回 ok

阶段 3 ·（建议）域名 + HTTPS

  1. 买域名（¥50–80/年）；国内服务器 + 域名需 ICP 备案（数周，免费）。想免备案改用香港区域服务器（延迟略增）。
  2. 装 Caddy 反代 :443 → :3000，自动签发 Let's Encrypt 证书；WebSocket 由 Caddy 透明转发，客户端同源逻辑不变。这样微信里也是"小锁"安全链接。
# Caddyfile
richman.example.com {
  reverse_proxy localhost:3000
}
不想买域名/备案？直接用 http://公网IP:3000 也能玩（微信里点"继续访问"即可）。HTTPS 是"体验+安全"升级，不是硬性前置。

阶段 4 · 真实异地联机验证

  1. 自己手机关 WiFi 用流量打开地址 → 建房成功。
  2. 拉 1 位异地亲友加入 → 走完两回合（掷骰、买地、结算广播正常）。
  3. 故意让一人刷新/断网 → 验证 session:resume 重连回局。

阶段 5 · 运维固化

  1. 备份存档：定时打包 /opt/richman/apps/server/saves/（cron + 传到对象存储/OSS）。
  2. 更新流程：git pull && pnpm install && pnpm build && pm2 restart richman（重启瞬间玩家刷新即回局，已有恢复机制兜底）。
  3. 监控：pm2 日志 + 进程内存告警；可选 UptimeRobot 探 /healthz。

阶段 6 ·（按需）横向扩展演进

  1. 当用户/房间数逼近单实例内存上限时，引入 @socket.io/redis-adapter + Redis，让多实例共享房间广播。
  2. 存档改为 Redis 或挂载共享卷；入口前加负载均衡并开启粘性会话。
  3. 此阶段才需要把"内存态"部分外移——朋友级规模前不要提前做，徒增复杂度。

5. 并发能力注意事项

  • 单实例天花板很高：每房间 ≤ 6 玩家 + 3 观战 = 9 条长连接；游戏是回合制，CPU 几乎只在 intent 时算一下规则，空闲时极低。一个 2C2G 实例轻松承载数百房间 / 上千并发连接。
  • 真实瓶颈是内存：房间状态常驻进程内存 + 每步写一份 <roomCode>.json。监控 RSS，估算：单房间状态几十 KB～几百 KB，数百房间约百 MB 级，2G 内存足够；但别让房间无限堆积（你已有 1 小时/24 小时回收策略，保持它生效）。
  • 事件循环是单线程：Node 单线程处理所有房间 intent。回合制下无压力；若未来做"秒级自动结算"等高密度定时器，注意别阻塞。
  • 压测建议：上线前用脚本开 50–100 个机器人房间跑半小时，观察内存/CPU/延迟，拿到你自己的容量基线，比拍脑袋靠谱。
  • 扩展代价：一旦要上多实例，必须 Redis Adapter + 共享存储 + 粘性会话（见阶段 6）。朋友级流量不要提前做。

6. 安全注意事项

公网暴露后，原有"熟人信任模型"失效。03 文档明写"拿到房间码即可加入，内部亲友不设防"。内网穿透时陌生人基本进不来；上公网后等于门牌号全网可试。
  • 房间码可枚举（4 位 = 10000 种）：陌生人可随机进房蹭玩或捣乱。缓解（按成本递增）：① 只通过"邀请链接 ?room=XXXX"分享，不公开播码；② 升到 6 位码（改 ROOM_CODE_COUNT，极小改动）；③ 给房间加密码/大厅锁（需改协议，工作量较大）。至少做①。
  • 无限流/无房间数上限：理论上可被脚本刷房耗尽内存。建议加：单实例最大房间数（如 500）、每 IP 建房频率限制、单 IP 最大连接数。
  • 无账号体系：token 只防"冒充重连"，不防"陌生人进房"。公网建议至少加房间密码或纯邀请制。
  • 明文传输：IP 直连用 http，昵称/操作明文。上 HTTPS（阶段 3）即可加密；同源部署无 CORS 暴露面。
  • 服务器本身：禁用 root 密码登录、SSH 仅限你的 IP、及时打补丁（unattended-upgrades）、pm2 以普通用户运行。
  • DDoS：轻量服务器带宽小，易被打满。朋友级一般无需高防；若被针对，再考虑前置 Cloudflare（注意国内访问变慢）或云厂商高防（贵）。

7. 稳定性注意事项

  • 单点故障：单实例 = 单点。进程崩溃 → pm2 秒级自拉起（房间由 saves 恢复）；但实例整机宕机 = 服务全停，直到你恢复。朋友级可接受；要 HA 就走方案 B 多副本（仍需 Redis）。
  • 重启丢失进行中牌局（当前事实）：房间仅存内存，服务器重启/崩溃/更新都会清掉所有牌局，玩家需重开。轻量服务器系统盘持久，但内存态仍随进程消失；若要"重启续局"须先实现 plan/03 §7 的 JSON 存档（独立任务）。
  • 优雅关闭已具备：已实现 SIGTERM/SIGINT 处理，部署时确保信号能传到进程（docker stop / pm2 默认会发 SIGTERM），让在途房间先落盘再退出。
  • 冷启动：常驻实例无冷启动；这正是避开 Serverless(FaaS) 的理由——FaaS 冷启动会掐掉长连接。
  • 延迟/区服：选离玩家近的区域；跨大区（如国内↔海外）延迟明显，体验差。海外玩家多用方案 C 或在当地部署。
  • 内存泄漏/长连接堆积：监控内存曲线；确保 lobby 空房即时回收、playing 全员离线 24h 回收（文档策略）真正生效，防房间无限增长。

8. 迁移期 / 迁移后检查清单

迁移期间（灰度）

  • 原内网穿透先保留作回退，云端验证通过再切换。
  • 把本地 saves/ 拷到云上，延续进行中牌局。
  • 若用域名，注意 DNS TTL，切换后等生效。
  • 小范围亲友实测（含断网重连），再全量告知。

迁移后（常态）

  • pm2 status online；/healthz 200。
  • 存档目录已持久化且定期备份。
  • 安全组仅放开必要端口；SSH 收紧。
  • 余额/流量告警已开；更新流程已固化。
  • 房间码改为只通过邀请链接分享（防蹭房）。
一句话路径：改 3 处小代码（0.0.0.0 / SAVE_DIR / /healthz）→ 买一台近区域轻量服务器 → pm2 跑起来 →（可选）Caddy + 域名上 HTTPS → 手机流量实测 → 固化备份与监控。朋友级流量单实例足够，将来涨了再提交同一个 Docker 镜像上 CloudBase 云托管。
